# NexaScan website SEO

The site is static HTML built by `scripts/build.mjs` and deployed by GitHub Pages. SEO is generated by the
build from one place, so most fixes are a front-matter or config change, never hand-edited HTML in `dist/`.

Read `references/site-policy.md` before changing anything: it says where each SEO signal comes from and what
this host can and cannot do. Google's rules (with sources) are in `references/google-search-rules.md`.

## Workflow

1. **See what changed.** `git status` and `git diff main --stat`. New or renamed pages under `src/pages/`,
   changes to `site.config.json`, `src/data/plans.json`, `src/layout.html` or `scripts/build.mjs` matter most.
2. **Build and audit.**
   ```bash
   npm run verify          # build + link check + SEO audit (the same gate CI runs)
   npm run seo -- --live   # optional: also checks the deployed site (status codes, 404, redirects)
   ```
   If git is not on PATH (this Windows machine), set `GIT` to the git executable first so the sitemap gets
   `lastmod` dates.
3. **Read the report.** `.seo-reports/report.md` (summary, findings, route inventory) and
   `.seo-reports/routes.json`. Each URL has separate attributes: `httpStatus`, `crawl`, `index`, `auth`,
   `canonical`, `inSitemap`. Do not collapse them into one label.
4. **Fix ERRORs** at their source (front matter, `site.config.json`, `scripts/build.mjs`), rebuild, re-run.
   ERRORs block the deploy in CI. Never silence a check to make it pass.
5. **Report WARNINGs** and fix the ones that are technical (image size, missing width/height, long titles).
   Owner-input warnings (`[… REQUIRED]` markers) need the owner: point to `docs/OWNER-DETAILS-NEEDED.md`.
6. **Content recommendations** go in a separate section of your reply, never mixed with technical findings,
   and are suggestions for the owner to approve. Base them on real user needs (support questions, Search
   Console queries), not keyword lists.
7. **After a deploy** nothing needs resubmitting: Google re-reads the sitemap once it has been submitted in
   Search Console. Owner-only steps are in `docs/SEO-MANUAL-STEPS.md`; optional API use is in
   `references/search-console.md`.

## Adding or changing a page

- Create `src/pages/<name>/index.html` with the front matter
  `<!--{"title":"…","description":"…","nav":"<key>"}-->`. Title and description must be unique and specific.
- Link it from the header, footer or a related page (the audit flags orphans).
- The build adds the canonical, sitemap entry and `lastmod` automatically. Keep a page out of search with
  `"index": false` (it then gets `noindex` and leaves the sitemap). Never use robots.txt for that.
- Product claims come from the app, not from marketing wishes: Free/Pro facts live in `src/data/plans.json`
  and must match the app's `product-catalog.json`. Check claims in the app repository before publishing.

## Rules

- Do not add ratings, reviews, FAQPage or SoftwareApplication markup without genuine, visible ratings and a
  current Google document that supports it. The audit refuses them.
- Do not create near-duplicate keyword pages, hidden text, or bulk-generated content.
- Do not use Google's Indexing API, sitemap pings or paid indexing services: they do not apply to this site.
- Do not claim that any change guarantees indexing, rich results or rankings.
- Do not commit credentials. `.gitignore` excludes the usual Search Console credential file names.
- Website changes go to a branch; pushing `main` publishes the site.

## What runs on its own

Nothing runs on a schedule because of this skill. The recurring check is CI: every push and pull request
to `main` runs `npm run verify`, and a failing audit stops the deploy. A periodic live check or Search
Console report needs an explicit schedule (a GitHub Actions `schedule` workflow, a Claude Code routine or a
desktop scheduled task), which the owner must approve and configure.
